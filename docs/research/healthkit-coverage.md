# @kingstinct/react-native-healthkit vs the §3.3 activity-signal catalog

**Ticket:** #17 · **Feeds:** the balance-engine build + §5 spike 1 (background shield-lift on earn) · **Date:** 2026-07-28

## The library, verified

- **Package:** `@kingstinct/react-native-healthkit` (repo `kingstinct/react-native-healthkit`) + peer `react-native-nitro-modules`. Same maintainer (Robert Herber / Kingstinct) as `react-native-device-activity` — one bus factor covers both of our OS-boundary libraries. 698 stars, 28 open issues, last push 2026-07-27 (yesterday): actively maintained.
- **Version:** **14.0.2** (npm latest, 2026-06-05). v9 (2025-06) was a full rewrite onto **Nitro Modules** (JSI, typed hybrid objects); v14.0.0 (2026-04-08) added the native cold-launch background-delivery engine. Release cadence is roughly monthly; master is ~7 weeks ahead of npm and contains at least two fixes we care about (see G1, G5).
- **Shape:** Expo config plugin (`["@kingstinct/react-native-healthkit", { background: true }]`, default on) sets the `com.apple.developer.healthkit` + `healthkit.background-delivery` entitlements and both Info.plist usage strings, and injects `BackgroundDeliveryManager.shared.setupBackgroundObservers()` into `AppDelegate.didFinishLaunchingWithOptions` — **but the published plugin is broken, see G1**. No Expo Go (dev client required — same constraint we already carry for device-activity). Works on simulator (unlike FamilyControls).
- **API model:** thin, faithful HealthKit mapping. Nitro hybrid objects per domain — `Core` (auth, observers, background, sources), `QuantityTypes` (samples, anchored queries, statistics), `Workouts` (anchored workout queries returning `WorkoutProxy` objects with live methods), plus category/correlation/etc. modules we don't need. Every sample carries `uuid`, `startDate`/`endDate`, `metadata`, `sourceRevision`, `device` — the full attribution set (verified in `ios/Serializers.swift`).
- **Query primitives that matter to us** (from `src/specs/*.nitro.ts`):
  - `queryQuantitySamplesWithAnchor(id, {anchor?, limit, filter?})` → `{samples, deletedSamples, newAnchor}` — real `HKAnchoredObjectQuery`; anchor is an opaque base64 string we persist. Deleted samples are surfaced, so revoked/deleted workouts can be un-credited if we ever want to.
  - `queryStatisticsForQuantity(id, ['cumulativeSum'], {filter?})` and `...CollectionForQuantity(..., anchorDate, intervalComponents)` — real `HKStatisticsQuery`, which is Apple's sanctioned way to total steps/energy: it **deduplicates overlapping samples from multiple devices/sources** (iPhone + Watch both counting the same steps), which a naïve sum over raw samples does not. Also `...SeparateBySource` variants for per-source totals.
  - `queryWorkoutSamplesWithAnchor({anchor?, limit, filter?})` — workout filter supports `workoutActivityType` and a first-class **`duration` predicate** (`{predicateOperator: greaterThanOrEqualTo, durationInSeconds}`), plus date/source/metadata/AND/OR/NOT.
  - Filters compile to real `NSPredicate`s natively (`ios/PredicateHelpers.swift`): metadata-key predicates, source lists, date ranges, and compound `AND`/`OR`/`NOT` — `NOT` wraps `NSCompoundPredicate(notPredicateWithSubpredicate:)`, which is exactly the correct idiom for the manual-entry filter (below).
  - `subscribeToObserverQuery(id, cb)` / `subscribeToChanges` — `HKObserverQuery` while the app is alive; callback delivers **only** `{typeIdentifier, errorMessage}` (no samples — by HK design), so the pattern is always observer-fires → run anchored query.
  - Auth: `requestAuthorization({toRead, toShare})`, `getRequestStatusForAuthorization` (should-we-prompt), `authorizationStatusFor` (write-side only — see auth notes), `useHealthkitAuthorization` hook.
  - Attribution helpers: `querySources(id)` (all sources that ever wrote a type), `currentAppSource()` (our own bundle — lets us exclude/recognize ExcerLock's own writes).

Gym presence (§3.4, location) and live walking (§3.5b, CoreMotion) are not HealthKit signals — out of scope here. Everything below is the §3.5 Apple Health rail.

Any activity type by default. | ✅ |
| S8 | **Workout type / distance / energy / duration reads** (dedup + card display + vendor cross-check) | `WorkoutSample`: `workoutActivityType` (75+ types), `duration`, `totalDistance?`, `totalEnergyBurned?`, `startDate`/`endDate`, `metadata`, `sourceRevision`, `device`, `uuid`; `WorkoutProxy.getAllStatistics()` for the iOS 16+ statistics-based totals. Everything §3.5c dedup needs (start-time window + type + source) is on the object. | ✅ |

## Background-delivery reality vs the PRD's claim-on-open stance

The PRD (§3.5) already promises only "reliably on open, best-effort in background." The library's v14 architecture is *better than* the naïve RN story, with one shipping defect:

- **Cold-launch registration is real.** Apple requires observer queries to be registered in `didFinishLaunchingWithOptions` for background delivery to relaunch a terminated app. v14 does this natively (`BackgroundDeliveryManager.setupBackgroundObservers()` reads persisted types before the JS bridge exists, uses a **nil predicate** explicitly so samples written while the app was dead aren't missed, queues events until JS subscribes). So: app terminated normally by the system → iOS relaunches us headless on new Health data → RN boots → we drain the observer event, run anchored queries, credit the balance, and (per device-activity report M2) call `unblockSelection` + re-arm the drain monitor. This is exactly §5 spike 1's happy path.
- **Force-quit is still fatal — as the PRD assumes.** A user swipe-kill stops HealthKit background launches until the next manual open (standard iOS behavior for background delivery; only exceptions like significant-location can resurrect a force-quit app). No library can fix this. The claim-on-open stance stays load-bearing.
- **Latency is dominated by Watch→iPhone sync, not by the observer.** `UpdateFrequency.immediate` is a ceiling, not a promise — iOS throttles delivery per type (steps/energy are batched; Apple Watch workout data only lands in the phone's HK store when the Watch syncs, typically minutes but up to much longer). Third-party apps (Strava et al.) write to Health whenever *they* sync. Spike 1 should measure the distribution but must not expect sub-minute unlocks; PRD wording already covers this.
- **The JS callback carries no samples** — `{typeIdentifier, errorMessage}` only. The engine's background wake handler is: observer event → anchored query per affected signal → credit → re-arm shields. Anchors make this idempotent across duplicate wakes (the `skipIf`-style guards we needed on the device-activity side are unnecessary here; the anchor is the guard).
- **The shipping config plugin does not install any of this** — see G1. Until patched, background delivery silently degrades to foreground-only and every claim happens on open (the app still works; spike 1 would just measure zero wakes).

## Authorization UX facts

- One up-front `requestAuthorization({toRead: [stepCount, activeEnergyBurned, appleExerciseTime, distanceWalkingRunning, distanceCycling, distanceSwimming, workoutType], toShare: […sim-mock types in dev builds only]})`. Querying a type never requested **crashes** (README warns; it's an HK behavior) — SignalKit must gate every query behind auth-requested state.
- **Read denial is invisible by design.** `authorizationStatusFor` reflects *write* permission only; a read-denied type just returns empty results. `getRequestStatusForAuthorization` says whether a prompt would show, nothing more. Onboarding must treat "no data" and "denied" as the same coaching state ("check Settings → Health → Data Access") — we can never display "you denied steps."
- **v14 regression (open, #352):** on cold start, apps where the user *denied* some types get a blank HealthKit sheet flashing up ~2–3 s after launch, triggered natively. Assigned to the maintainer; downgrading to 13.4.0 avoids it. Watch this before pinning (G5).

## Simulator behavior + the SignalKit mock boundary

HealthKit **runs on the iOS simulator** (Health app present, `isHealthDataAvailable()` true) — unlike FamilyControls. That splits our test loop cleanly:

**Real-on-simulator (no mock needed):** the entire read pipeline. A dev-build seeding harness can write genuine HK data via `saveQuantitySample` (steps, active energy, distances) and `saveWorkoutSample` (activity type, start/end, totals, metadata) and then exercise the *production* code path: anchored queries, statistics dedup, duration predicates, observer-fires-while-foregrounded (observer queries do fire on sim when data is written), auth flows. Crucially, `HKWasUserEntered: true` **can be set in save metadata**, so the manual-entry filter is testable against real HK predicates on sim.

**Must be mocked above HealthKit (the SignalKit interface line):**
1. **Source attribution variety** — HK stamps every save with the *saving app's* source; the sim can never produce a sample that appears to come from Strava/Garmin/Health-app-manual (bundle-id level). Cross-source dedup (S10) and bundle-id-based attribution logic need fixture `sourceRevision`/`device` objects injected at the SignalKit boundary.
2. **`appleExerciseTime`** — read-only; unwriteable everywhere. Active-minutes conditions are only testable via injected fixtures (or via the S6 workout-duration fallback path, which *is* seedable).
3. **Background-delivery wakes** — headless relaunch on new data is not reliably reproducible on sim; mock = invoke the SignalKit "observer fired" entry point directly. Physical-device smoke suite (already mandated by the map for shields/geofence/motion) gains one HealthKit case: §5 spike 1.
4. **Watch-sync latency** — timing distributions are device-territory; sim tests treat freshness as instant.

**Concrete boundary recommendation:** SignalKit exposes one `HealthProvider` interface — roughly `requestAuth()`, `getNewSamples(signal, sinceAnchor)`, `getTodayTotal(signal)`, `onChange(signal, cb)` — with a library-backed impl and a fixture impl. Every screen and the whole condition engine run on the fixture impl in the simulator loop (Maestro); the library impl is additionally integration-tested on sim via the seeding harness for S1–S5/S7/S9; S10 fixtures + S12 wakes round out coverage. That makes **every screen testable on simulator** with zero physical-device dependency, matching the map's locked test strategy.

## Gaps / risks, ranked

1. **G1 — Published config plugin never wires cold-launch background delivery** (S12). `app.plugin.js` in npm 14.0.2 predates the AppDelegate injection entirely (verified in the tarball: zero references to `BackgroundDeliveryManager`), and even the TS source's regex missed Expo SDK 53+ multi-line Swift signatures. Both fixed on master (PR #367, merged 2026-07) but **unreleased**. Action: after prebuild, assert the AppDelegate contains `setupBackgroundObservers()`; until the next npm release, patch-package the compiled plugin (the fix is small) or vendor a one-line config plugin of our own. Silent failure mode — build a CI check, don't trust it.
2. **G2 — Active minutes are Watch-only and read-only** (S6). iPhone-only users read ~0 exercise minutes; the signal can't be seeded on sim. Product fix: catalog copy prefers "workout minutes" (S7 duration path, works for everyone) and surfaces exercise-minutes conditions only when a Watch/`appleExerciseTime` source is detected (`querySources`).
3. **G3 — Statistics vs anchored-ledger split must be designed, not improvised.** Rates need *today's deduped total* (statistics query); events on workouts need *exactly-once per workout* (anchored query). Mixing them naïvely double-counts (raw sample sums ignore iPhone+Watch overlap) or misses (statistics have no per-item identity). The balance engine spec should name, per signal, which primitive is the ledger source. This is an us-design task, not a library gap.
4. **G4 — Open bug: stale foreground reads (#330).** One reporter (Watch heart-rate polling): fresh samples invisible to queries until the app is backgrounded ~5 s or killed. Unresolved, cause unknown, possibly setup-specific. Our claim-on-open flow does a query right after foregrounding (not long-running foreground polling), which is the pattern that works in their report — but spike 1 should include a "workout on Watch → open app → is it claimable?" case to confirm on our stack.
5. **G5 — v14 pin decision.** v14.0.2 open issues: auth-sheet flash on cold start (#352), a closed-but-fix-unreleased Swift crash in the workout query path on iOS 26 (#366), `getWorkoutRoutes` memory leak (#370 — we don't use routes). Options: pin 13.4.0 (loses the native background engine, which was the point of v14) or pin 14.0.2 + patch-package G1 + retest #352 on our auth set (we request everything up-front, and the flash reportedly needs *denied* types). Recommendation: start on 14.0.2+patch, keep 13.4.0 as the escape hatch, upgrade the moment the next release lands (master already contains the G1/G5 fixes).
6. **G6 — Read-permission opacity** (auth section). Not a bug — Apple design — but onboarding and the "why is my condition not earning?" support surface must be written around "no data ≠ visible denial."
7. **G7 — Single-maintainer dependency** (process). Same posture as device-activity: pin exact versions, keep patch-package in the toolchain, budget for upstreaming. Upside: one maintainer relationship covers both critical libraries.

**Overall verdict:** every v1 catalog signal has a concrete, source-verified API path; there is no capability gap requiring a different library or custom Swift. The risks are release-hygiene (G1, G5) and engine-design decisions (G3), plus one Watch-dependency product tweak (G2).
