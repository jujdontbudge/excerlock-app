# react-native-device-activity vs every PRD §3 Screen-Time mechanic

**Ticket:** #16 · **Feeds:** the §5 device spike triad · **Date:** 2026-07-28

## The library, verified

- **Package:** `react-native-device-activity` (repo `kingstinct/react-native-device-activity`, monorepo `packages/react-native-device-activity`).
- **Version:** **0.6.1** (npm latest, published 2026-02-19). v0.6.0 (2026-02-17) added web-content filtering + iOS 15 authorization; v0.5.0 (2025-06) added `startMonitoring`/`stopMonitoring` as background *actions* — load-bearing for Walk & Scroll.
- **Maintenance:** active — last push 2026-03-09, responsive maintainer. **Bus factor = 1** (Robert Herber / Kingstinct), 173 stars. Regen ships it in production (PRD §10.9), which is our existence proof; still, plan for fork-and-patch capability.
- **Shape:** Expo config plugin (`{ appleTeamId, appGroup }`) that generates **three native targets** — `ActivityMonitorExtension`, `ShieldConfiguration`, `ShieldAction` — plus the app module. Deployment target iOS ≥ 15.1. No Expo Go, ever (`expo-dev-client` mandatory, as §10.9 already states). FamilyControls *distribution* entitlement must be requested **once per bundle ID = 4 requests** (app + 3 extensions); until granted, not even an EAS dev-client build — local Xcode builds only.
- **Core architecture:** everything crosses process boundaries via **app-group UserDefaults**. The app writes config (selections by ID, shield configs by ID, action lists keyed `actions_for_{activity}_{callback}_{event}`); the OS-side extensions read and execute it. This is what makes the OS-side behavior survive force-quit — and it is also the ceiling: extensions only *execute pre-declared action lists*, they run no JS and no app code.

**API surface (from `src/*.ts` + `ios/` + `targets/` of the 0.6.1 tarball, not from the README alone):**

- *Auth:* `requestAuthorization("individual"|"child")`, `revokeAuthorization`, `getAuthorizationStatus`, `pollAuthorizationStatus` (status caching is buggy OS-side; polling + app-restart workarounds documented).
- *Selection:* `DeviceActivitySelectionView` / `...SheetView` (+ `Persisted` variants keyed by `familyActivitySelectionId`), `setFamilyActivitySelectionId`, set-ops (`union`, `intersection`, `difference`, `symmetricDifference`), `activitySelectionMetadata` (counts only), `isEqual` / `isSubsetOf`.
- *Blocking:* `blockSelection`, `unblockSelection`, `enableBlockAllMode` / `disableBlockAllMode`, whitelist ops (`addSelectionToWhitelistAndUpdateBlock`…), `resetBlocks`, `isShieldActive`.
- *Monitoring:* `startMonitoring(name, schedule, events[])`, `stopMonitoring`, `getEvents`, `onDeviceActivityMonitorEvent` (app-alive only), `onDeviceActivityDetected`; callbacks: `intervalDidStart/End`, `eventDidReachThreshold`, warning variants.
- *OS-side actions* (`configureActions`, run inside the monitor/shield extensions with the app dead): `blockSelection`, `unblockSelection`, `enableBlockAllMode`, `disableBlockAllMode`, whitelist ops, `sendNotification`, `sendHttpRequest`, `setBadgeCount`, `startMonitoring` / `stopMonitoring`, web-filter ops, `openApp` (**broken**, see G1) — each with idempotency guards (`skipIfAlreadyTriggeredWithinMS`, `skipIfLargerEventRecordedAfter`, `neverTriggerBefore`, `sleepBefore/After`…).
- *Shield:* `updateShield(config, actions)` + per-selection `updateShieldWithId`; config = Apple's fixed `ShieldConfiguration` fields only; text supports **placeholders** (`{applicationOrDomainDisplayName}`, `{familyActivitySelectionId}`, `{token}`, `{tokenType}` — nothing app-defined).
- *Plumbing:* app-group `userDefaultsSet/Get/…`, `getAppGroupFileDirectory`, `moveFile`/`copyFile` (shield icons), `reloadDeviceActivityCenter`, `refreshManagedSettingsStore`, `clearAllManagedSettingsStoreSettings`.

**Hard OS limits the design must respect (confirmed in code/issues, not just docs):**

1. **20 concurrent monitors** max (README; Apple limit).
2. **15-minute minimum monitoring interval** — `DeviceActivityCenter` rejects shorter intervals. Community-validated workaround (issue #79): **backdate `intervalStart` into the past** so the *future* portion is short (e.g. start = now − 14 min, end = now + 1 min). Unofficial but widely used.
3. **Thresholds measure cumulative *usage* of the selection within the interval, not wall-clock time** (issue #79 confirms the confusion is common). `includesPastActivity` (counts usage earlier in the interval) exists in the API but is **iOS 17.4+**; below that the library silently passes `false`.
4. Extension execution is **static**: action payloads are declared ahead of time; the only dynamic values are the placeholder strings above. No arithmetic, no "compute remaining balance" OS-side.
5. Monitor extensions have a small jetsam memory budget (~6 MB class); interval callbacks can fire with minutes of jitter and thresholds can lag usage slightly. Nothing here is real-time-guaranteed.

## The mapping: every §3 mechanic that touches Screen Time

**Verdicts:** ✅ supported as-is · 🟡 supported with workaround · 🔴 gap needing custom Swift (or a product change).

| # | PRD mechanic | Library/OS reality | Verdict |
|---|---|---|---|
| M1 | **Shield apply / lift on the locked group** (§3.1, §3.6) — shields up when balance empty, lifted on earn; OS-enforced through force-quit/reboot | `blockSelection` / `unblockSelection` by persisted `familyActivitySelectionId`; ManagedSettings shields survive force-quit and reboot natively. One selection = our one locked group. | ✅ |
| M2 | **Background shield-lift on earn** (§3.5, §5 spike 1) — HealthKit background delivery wakes app → balance credited → shield lifts without app open | Not a DeviceActivity feature at all: when iOS wakes us (HealthKit background delivery / geofence), the *app process* calls `unblockSelection` + re-arms monitors — all module functions work from background execution. The PRD already prices in best-effort wake timing. Must also rewrite the drain monitor (M5) in the same wake. | ✅ (detection timing is the §3.5-accepted best-effort, not a library gap) |
| M3 | **Mid-day threshold re-arm** (§3.1/§3.3, §5 spike 2) — earn adds time → the "balance empty" trip-point moves | Events are **fixed at `startMonitoring`**; no "update threshold" API (Apple's, not the library's, omission — issue #74 documents it). Standard pattern: `stopMonitoring` → `startMonitoring` with the new event set + `includesPastActivity: true` so usage already spent today still counts toward the new thresholds. **iOS < 17.4 has no `includesPastActivity`** → naïve re-arm forgets today's usage and over-grants. Alternatives for old iOS: derive an offset from already-fired tick events (M5) and shrink the new thresholds accordingly — fiddly, spike must decide (or we set min iOS 17.4). | 🟡 |
| M4 | **Day boundary reset** (§3.1, §3.10 day-boundary setting) | A repeating 24 h monitor (`intervalStart` at the user's boundary hour) with `intervalDidStart` actions: `unblockSelection`/reset + notification. Custom boundary time = plain `DateComponents`. Runs OS-side even if the app hasn't been opened in days. | ✅ |
| M5 | **Real-time drain / usage metering of the locked group** (§3.1) — balance drains as one shared pool while locked apps are used | Screen Time offers **no usage query API**; the only OS-side signal is threshold events. Standard workaround (README "Time tracking"): ladder of named events (`min_1`, `min_2`, … `min_N`) on one monitor; each `eventDidReachThreshold` = one tick, persisted to app-group UserDefaults (`getEvents`) and executable OS-side (final tick = `blockSelection`). Balance display between ticks is interpolation; ticks lag usage slightly. Event-count ceiling per monitor is undocumented — spike must probe (we need up to ~`daily-cap` events/day at 1-min granularity). The `DeviceActivityReport` extension shows exact numbers but **cannot share data back to the app** (sandboxed; confirmed in issue #64) — display-only, not a ledger source. | 🟡 |
| M6 | **Schedules & lock windows** (§3.10–3.12) — active/rest/custom days, lock-window hours, one-off overrides, vacation | `DeviceActivitySchedule` supports `weekday` DateComponents + `repeats`; ≤ 20 monitors is plenty for 7 weekday schedules + drain + walk-session monitors. Rest days / vacations / sick tokens = the app (or an `intervalDidStart` action set) simply not arming that day's monitors — economy logic stays in JS; the OS side just needs the *current* day armed correctly, re-synced on every app open/wake. One caveat: a schedule *change while the app is dead* (e.g. vacation delay elapsing) needs a pre-armed monitor or waits for next app open — plan the arming strategy. | ✅ |
| M7 | **Custom shield content** (§3.15 shield screen: "sells, never scolds — balance state, nearest path to unlock, button into ExcerLock") | Apple's fixed template only: blur/bg color, icon (SF Symbol or **app-group image file** — our brand mark works), title, subtitle, primary + secondary button labels/colors. No custom layout, no live countdown, no banner art. "Balance state" text = re-write shield config (`updateShield`) whenever the app runs, or swap between a few pre-written shield configs (`shieldId` per state) from OS-side actions — so wording is *state-fresh*, not *minute-fresh*. Per-selection shields exist but selection→shield matching is a documented best-guess heuristic (README notes). Copy must be designed for staleness ("Out of time — walk to keep scrolling"), not live numbers. | 🟡 |
| M8 | **Shield buttons → open ExcerLock / start a walk** (§3.15, §3.5b "shield screen's button deep-links in") | **The one true gap.** Shield action extensions cannot officially launch the host app. The library's `openApp` action is a no-op (open issue #81; maintainer confirms) and its `openUrl`/`openUrlWithDispatch` shield actions use the `NSExtensionContext().open()` hack — a freshly-created context not connected to the host, which does not reliably work (some shipping apps have found private-ish tricks; nothing supported). Reliable options: shield button fires `sendNotification` (works from the extension) with a deep link the user taps — two taps instead of one — or the button just closes and the user opens ExcerLock manually. This shapes the most-seen surface in the product; needs on-device truth. | 🔴 (custom Swift experiment in a forked ShieldAction target; product fallback = notification tap-through) |
| M9 | **DeviceActivity events / monitor callbacks generally** (earn-side nudges §3.14, warning events) | `intervalWillStart/EndWarning`, `eventWillReachThresholdWarning` all surfaced; OS-side `sendNotification` action covers "balance low / empty / shields up" notifications with the app dead. JS listener works only while app is alive — fine, we consume history via `getEvents` on open. Idempotency guards (`skipIf…`) exist for the re-arm/restart cases. | ✅ |
| M10 | **App-group token selection** (§3.6 — apps as opaque tokens, one locked group) | First-class: persisted selection IDs in the app group, picker views (sheet + inline), metadata counts, set-ops. Known sharp edges: the SwiftUI picker **crashes** under load (README recommends a fallback view behind it — build one); iOS silently **auto-promotes** N individually-picked apps into a category token (open issue #95) — harmless for our single-group model but metadata counts become unreliable, so never build UI/logic on `applicationCount`. | ✅ (with picker-fallback UI hygiene) |
| M11 | **Always-exempt apps** (§3.6 — Phone, Messages, Maps, ExcerLock never locked) | Tokens are opaque **both ways**: we cannot programmatically identify or subtract "Messages" from a user's selection. Phone/emergency is exempted by the OS itself; everything else is onboarding guidance ("don't select these") — a category selection will happily shield Messages. ExcerLock itself can't end up in the selection in practice (user must actively pick it; coach against it). No library fix possible — Apple's privacy design. | 🟡 (product/onboarding mitigation, not code) |
| M12 | **Walk & Scroll: shields lifted while walking, renewable-increment fail-safe** (§3.5b, §5 spike 3) | The architecture the PRD demands is exactly expressible: on each verified walking check the app calls `unblockSelection` + (re)starts a short monitor whose `intervalDidEnd` action is `blockSelection` — the re-shield lives OS-side and survives force-quit, capping the exploit at one increment. **But** the 15-min minimum interval means honest short increments (PRD wants "short renewable") require the **backdated-`intervalStart` hack** (issue #79 pattern; the `startMonitoring` *action* even takes `intervalEndDelayMs` for this). Unofficial; iOS-version-sensitive; plus interval-end jitter means re-shield is ~0–2 min late. Grace-period design already absorbs lag. If the hack proves flaky: increments become 15 min (weaker fail-safe, still bounded) — product-acceptable fallback but test first. | 🟡 |
| M13 | **Usage increments as the Walk & Scroll watchdog** (ticket's "usage increments" item) — detect the user actively scrolling during a session, catch the force-quit exploit | Two complementary uses, both supported: (a) the renewable increment itself (M12); (b) a 1-minute threshold ladder (M5 pattern) scoped to the session monitor tells us *the locked apps are actually in use* while walking verification runs — e.g. drain-at-reduced-rate accounting per §3.5b, and a dead-man's-switch (`eventDidReachThreshold` action → `blockSelection` if the session monitor wasn't renewed). Same caveats as M5 (tick lag, event-count ceiling). | 🟡 (inherits M5's workaround) |
| M14 | **Full-Lock mode** (§3.2 — allowance 0, shields from day boundary until first earn) | Degenerate case of M1+M4: day-boundary monitor's `intervalDidStart` action = `blockSelection`; first earn = M2. No extra machinery. | ✅ |
| M15 | **"Time reclaimed" & usage stats** (§3.13) — needs actual locked-group usage | Only source is our own tick ledger (M5) — approximate to ±1 tick, and blind for periods when no monitor was armed. `DeviceActivityReport` (exact data) is display-only (M5). PRD's number is a monthly aggregate marketing stat, so tick-resolution is fine — but state clearly in the build spec that this is derived from tick events, not ground truth. Per-app breakdown already excluded from v1 (§3.15). | 🟡 |
| M16 | **Web domains in the locked group** (implied by picker; §3 speaks of apps) | Selections carry web-domain tokens; shields cover Safari per-domain; v0.6 adds a separate whole-web-content filter policy. Available if we ever want "block mobile web YouTube too" — no v1 requirement. | ✅ (bonus, unused) |

## Gap list, ranked by risk

1. **G1 — Shield → app deep-link is broken** (M8, 🔴). Highest product impact: the shield is the most-seen surface and both its CTAs ("Start a walk", "into ExcerLock") assume launching the app from the shield. `openApp` is a confirmed no-op; the `openUrl` hack is unsupported. Either a forked `ShieldAction` extension finds a working technique on current iOS, or the shield UX is redesigned around notification tap-through / manual open. Decide from device evidence, not hope.
2. **G2 — Sub-15-minute unlock increments rely on the backdated-interval hack** (M12, 🟡). The Walk & Scroll fail-safe's strength is set by the shortest reliable increment. The hack is community-proven but unofficial and jitter-prone; if it fails on target iOS versions the fail-safe degrades to 15-min increments.
3. **G3 — Mid-day re-arm usage continuity** (M3, 🟡). `includesPastActivity` is iOS 17.4+. Below that, every earn-driven re-arm forgets the day's spent usage. Options: min-iOS 17.4, or tick-offset compensation (M5-derived), or accept over-grant on old iOS. This decision gates the balance engine design.
4. **G4 — Drain metering is a threshold-ladder approximation** (M5/M13/M15, 🟡). Undocumented event-count ceiling per monitor, tick lag, and re-arm cost every time balance changes. The whole §3.1 economy sits on this pattern — it must be load-tested, not assumed.
5. **G5 — Shield content is static-template only** (M7, 🟡). No live balance, no custom layout, art limited to one icon image. Pure design constraint; shield copy system (pre-written per-state configs) needs to be specced.
6. **G6 — Exempt apps not programmatically enforceable** (M11, 🟡). Onboarding copy + selection review UX; zero code fix exists.
7. **G7 — Picker fragility** (M10, 🟡-hygiene). SwiftUI picker crashes and category auto-promotion; needs fallback UI and no logic on selection counts.
8. **G8 — Single-maintainer dependency** (process). Fork/patch-package readiness (the three extension targets live in the package's `targets/` — customizing G1 already implies forking them); pin versions; budget for upstreaming.

**Custom-Swift verdict:** only **G1** clearly needs custom Swift (patched/forked ShieldAction target). Everything else is achievable through the library's action system — the monitor-extension action DSL (with `skipIf` guards, `startMonitoring`-as-action, placeholders) is expressive enough that v1's OS-side logic should not require touching the ActivityMonitor extension. Fallback if G3/G4 spikes fail on old iOS: a forked ActivityMonitor extension that computes threshold offsets natively — keep as contingency, not plan.

## What the §5 device spike triad must cover

PRD §5 names three spikes. Mapped to the gaps above, with explicit exit questions:

- **Spike 1 — background shield-lift on earn** (M2 + G3-adjacent): HealthKit background-delivery wake → credit → `unblockSelection` + full monitor re-arm, app in background/force-quit. Measure wake latency distribution; verify ManagedSettings + `startMonitoring` calls succeed from background wake; verify the re-armed drain monitor (G4) is consistent afterward.
- **Spike 2 — mid-day threshold re-arm** (G3 + G4): stop/start monitors mid-interval with `includesPastActivity` on iOS 17.4+ **and** on one pre-17.4 device; probe the event-ladder ceiling (arm 200+ events); confirm no double-fire with `skipIf` guards across restarts; decide min-iOS / compensation strategy. Exit = a written balance-engine re-arm algorithm.
- **Spike 3 — Walk & Scroll runtime + live re-shield** (G2 + M13): backdated-interval hack across target iOS versions; re-shield latency at interval end (jitter measurement); force-quit mid-session → confirm one-increment cap; session tick events for reduced-drain accounting; extension memory headroom with our action payloads.
- **Fold into spike 3 (or a half-day spike 4): G1** — on-device test of `openUrl`/`openUrlWithDispatch` from the ShieldAction extension on current iOS, plus the notification-tap-through fallback timing. The shield-screen design (§3.15) cannot be finalized until this answer exists.
