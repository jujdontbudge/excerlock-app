## 3. Evidence-backed external research (as consulted 2026-09-29)

### Official Apple rules and test boundaries — tier A

- [App Review Guidelines §§2.1(a), 2.1(b), 2.3/2.3.3, 2.3.1, 2.4.1, 2.5.1, 3.1.2, 5.1](https://developer.apple.com/app-store/review/guidelines/): Apple says test **on-device** before submission, include a working demo account when login is required, make all IAPs functional and visible, and show the **app in use** (not title art/login/splash) in screenshots. Text/image overlays are allowed. An iPhone app should run on iPad whenever possible. Native capabilities have to be used for their intended purpose and described; removing unused HealthKit was the right response to the older 2.5.1 finding. A file-size/metadata validator cannot judge visual truth or live purchase behavior.
- [App Review Information](https://developer.apple.com/help/app-store-connect/reference/app-review-information/) explains non-expiring demo credentials (when login is required), Notes for testing settings/account details, and the 4,000-byte Notes field. Anonymous use does not excuse an inaccessible paywall; review notes must match the *actual* submitted build and physical-device needs. [Upload screenshots](https://developer.apple.com/help/app-store-connect/manage-app-information/upload-app-previews-and-screenshots/) covers device-size sets and Media Manager; guideline 2.3.3, not a dimension check, is the semantic rule.
- [Testing subscriptions and IAP in TestFlight](https://developer.apple.com/help/app-store-connect/test-a-beta-version/testing-subscriptions-and-in-app-purchases-in-testflight/) says TestFlight apps run in **sandbox**, supports Sandbox Apple Account controls, and renews subscriptions daily up to six times in a week. [Sandbox account settings](https://developer.apple.com/help/app-store-connect/test-in-app-purchases/manage-sandbox-apple-account-settings/) cover reset history/interrupted purchases/renewal controls. Xcode local `.storekit` configuration and sandbox/ASC-backed TestFlight are **different environments**; a fake or local StoreKit response does not validate product availability, agreements, Adapty mapping or App Review's sandbox. Apple's rejection itself says products **need not be previously approved** to function in review; don't blame `READY_FOR_REVIEW` state alone.
- [Family Controls entitlement request](https://developer.apple.com/documentation/familycontrols/requesting-the-family-controls-entitlement), [AuthorizationCenter](https://developer.apple.com/documentation/familycontrols/authorizationcenter) and local measured `docs/research/familycontrols-on-simulator.md`: distribution entitlement/extension signatures and individual authorization are separate from *actual shielding*. The local August 2026 study specifically corrected earlier overstatements: a fresh simulator can report silent authorization, but denial and actual target-app shielding were not proved. `docs/adr/0042-ota-ready-native-sensor-surface-and-review-port.md` records unavailable motion streams on simulator. A device is needed for selected-app shield, walk-to-Met/Unlock, background/force-quit behavior, gym location and real permission dialogs; a test of a preview card proves none of them.
- [Reply to App Review](https://developer.apple.com/help/app-store-connect/manage-submissions-to-app-review/reply-to-app-review-messages/) explicitly allows **same-build** resubmission for a *metadata-only* rejection after correction. This submission also has a 2.1(b) functional issue; that exception alone does not clear it. [Unresolved-issues procedure](https://developer.apple.com/help/app-store-connect/manage-submissions-to-app-review/manage-a-submission-with-unresolved-issues/) requires editing/resubmitting all rejected items; it warns that removed items cannot be re-added to the same submission. No action here authorized a reply, upload or resubmit.

## 4. Smallest prevention plan (no new test suite)

The policy is **ARCHITECTURE rule 7 / ADR 0045: no tests by design**. Maintain a short static + focused simulator + physical distribution proof; **do not** import a sprawling XCTest/Jest/Maestro suite by stealth. Any change to that core rule needs an explicit ADR based on `docs/adr/TEMPLATE.md`. A *regression proof of this fix* should fail on old code and pass on the candidate under a controlled identity delay; if that cannot be done within a focused proof, record the limitation rather than claiming it. Do not count a proof that only sees the fake runtime as proof of Adapty/StoreKit.

No immediate code change to the shipping app is part of this report. ## 5. Cannot-guarantee-no-rejection risk register

| Risk and classification | Signal / decision boundary |
|---|---|
| **Identity/SDK race (code bug, high)** | Sentry + source match. Fix may time out if canonical auth/API remains unavailable; “wait 15 seconds” is not a guarantee. Stop on real TestFlight error; attach issue event/build and reproduce before asserting root cause. |
| **Promotional metadata (policy violation, high)** | Uploaded six mockups are known bad per Apple. Full-UI image set still requires human Apple judgment and truthful claims; no static image hash can certify policy compliance. |
| **Family Controls / motion / gym (native device gap, high)** | Simulator silent grant or fake Shield preview is not real Enforcement. Distribution entitlement, background launch, force-quit, Always-location, schedule transitions and iOS-specific behavior need physical proof; some force-quit behavior is an admitted product limit (ADR 0040). |
| **StoreKit sandbox, offers, eligibility, reviewer account/device (external/edge, high)** | Products may be attached and valid yet be absent to a specific account/region, already subscribed, interrupted, or show different trial terms. Paid Apps Agreement status needs holder verification; Apple's wording does not prove it is inactive. Capture product IDs and screenshots without customer data. |
| **iPad review of nominally iPhone app (compatibility, medium/high)** | Apple used iPadOS 27.0 despite `supportsTablet:false`. Do not assume an iPhone-only setting prevents iPad review; ensure purchase/error state and screen layout remain usable, and explain iPhone motion-only path without an artificial reviewer bypass. |
| **Remote flags, OTA and stale artifact (configuration/release, medium/high)** | Debug proofs, TestFlight binary, ASC build and OTA can differ; the `review_preset` flag was briefly 100% after submission. Freeze reviewed behavior, compare installed build/runtime/flags at proof time; new capability/flag scope calls for a new submission under `docs/ota.md`, not a hidden OTA switch. |
| **Privacy, account deletion, policy interpretation (policy/operational, medium)** | Metadata/App Privacy, location/camera copy, account access after lapse and deletion may be reviewed on a different path. Check ADR 0024/0048 and current guideline; if Apple disagrees with an honest feature, respond with precise evidence or use the formal appeal route rather than conceal it. |
| **Reviewer/Apple variance (irreducible)** | Different hardware, language, OS, sandbox state and evolving guideline interpretation can yield a new finding. An approved build is evidence of that review, **never a guarantee for the next**. Preserve exact complaint and learn, don't inflate a simulator green to “no rejection possible.” |

**Evidence-handling rule:** retain curated build/proof manifests and redacted reviewer wording, not raw transcripts, private screenshots, purchase receipts or step/location/app-selection data. Git docs have older paths and stale statements; use the exact Build 12 artifact and current ASC readback as the release truth. Any proposed release requires the user's explicit permission and the shared lock in `docs/agents/operations.md`.
