# Purchase path incident audit — 2026-10-21

Scope: Continue on the Paywall, identity readiness, Adapty activation/identify, placement/product loading, Apple checkout results, restore, durable recovery and client payment analytics. Worktree `t3-5a0d7f80`, branch `t3/purchase-path-robustness`, base `269885cc`. No production writes, releases, pushes or merges. The lead's Paywall close/reset and integration-identifier changes are deliberately excluded.

## Findings ranked by expected lost revenue

1. **Observed pre-Apple purchase veto: integration identifiers.** `app-next/src/packages/subscription/AdaptySubscriptionAdapter.ts:427`, called at lines 304 and 367; the identity spine also calls integration attachment at `identity/lib/identityCoordinator.ts:225`. Missing PostHog distinct ID throws, and a failing Adapty identifier upload prevents `makePurchase` or restore. The incident's error 2005 is consistent with this path; the brief establishes the blocking call sequence, but a 2005 alone does not identify the failed endpoint. Likelihood: a purchase failure is confirmed in production; any temporary identifier failure can veto a willing buyer. **Lead-owned fix; unchanged on this branch.** The same lead owns `paywall/PaywallSlot.tsx:71` sending Close back to O01. Integrate those fixes with this branch before release.

2. **A failed activation permanently poisons the session; an audience write can veto every plan load.** `AdaptySubscriptionAdapter.ts:104` formerly retained a rejected `activation` promise forever, so later readiness retries could never recover. The optional `onboarding_offer_version` update at line 228 formerly threw before products were requested. A brief outage could therefore become a whole-session inability to pay, including with a valid fallback file. Likelihood: high conditional on a single startup network failure; production incidence unmeasured. **Fixed:** bounded backoff, rejected-promise reset, identity checks per attempt and best-effort audience update. The installed React Native SDK's activation waiter does support a later retry; no SDK patch is necessary.

3. **An uncertain or charged purchase loses its local recovery record.** `AdaptySubscriptionAdapter.ts:308` formerly cleared every pending journal and attribution intent on every exception from the purchase call. The old-code proof has one purchase, one scripted StoreKit grant and `recovery:"none"` after an interrupted response. Adapty iOS 4.0.2's unverified-transaction branch maps some transaction verification errors to **2005**, so that number does not prove nonpayment. Its plugin can also emit **2009** when encoding the successful purchase response (`Request.MakePurchase.swift:33`, `AdaptyJsonData+Result.swift:34`); the installed core bridge explicitly describes 2009 as a response encoding failure. Likelihood: plausible for interruptions, generation/profile changes and transaction verification failures; response encoding failures are expected to be rarer, and production frequencies are unmeasured. **Fixed:** retain uncertain/network/encoding/decoding/profile-change recovery and interrupted attribution intent, never automatically resubmit the payment call, and save a returned successful transaction's original ID/environment before checking a changed live identity. The original checkout account still owns the journal; no other account is admitted.

4. **One AsyncStorage failure can poison all recovery writes; failed clear can look like no recovery.** `subscription/PurchaseRecoveryJournal.ts:62` and line 110. The original write chain continued only on fulfillment and published state before persistence. A failed confirmation could block every later restore confirmation, and a failed clear advertised `none` even though the pending disk record remained. An initial read rejection was also permanent. Likelihood: lower than vendor network failures, high impact for affected paid users; fault injection establishes behavior, not production prevalence. **Fixed:** retryable hydration, serialized mutations that commit to disk before publishing, a recovered write tail, and one 300 ms retry for journal removal. Pending recovery remains authoritative if persistence still fails.

5. **The payment funnel is systematically invisible.** `telemetry/PostHogAnalyticsAdapter.ts:147` rejected every `purchase_`, `restore_`, `trial_` and `subscription_` prefix after checking the registry. The registry explicitly owns `purchase_started`, `purchase_failed`, all three restore diagnostics and `subscription_verification_failed` on the client. `paywall_error` was unaffected, explaining the incident's exact event pattern. The filter appears in source commits `53054052` (build 19 checkout), `81a9f623` (build 20 checkout) and the current branch, and was introduced by `0d6841dc` on 2026-10-13. The build 21/22 incident is consistent with that source; their signed archived JS artifacts were not fetched. Likelihood: deterministic for every affected capture, independently of SDK flushing. **Fixed:** the client-owned registry is the only event-name allow-list. Vendor-owned revenue/subscription events remain excluded. Existing consent and generation gates are unchanged. Failure classes now distinguish network, declined and unavailable SDK errors instead of calling every exception unknown.

6. **A same-frame double tap can produce a false failure and duplicate intent analytics.** `paywall/lib/PaywallScreen.tsx:107` formerly relied on React state becoming busy. The subscription adapter already set busy synchronously, preventing a second StoreKit call; the second UI invocation could still log another intent and show an error for the busy rejection. Likelihood: occasional impatient double taps, usually an apparent failure rather than a duplicate charge. **Fixed:** one synchronous screen guard shared by purchase and restore, released in `finally`. Same-frame native tap delivery itself was not reproduced; the guard and existing adapter serialization were source-reviewed.

## Scenario coverage and remaining boundaries

- **Activation not finished / slow activation:** purchase and plan loading await the identity-ready spine; native SDK methods also await activation. The existing 15 s readiness budget remains. Transient activation/identify failures retry twice and a final failure no longer poisons later attempts. A genuinely hung SDK operation cannot safely be abandoned while another identity transition runs; no false success or parallel checkout is introduced.
- **Products absent, stale or unavailable:** placement and product requests retry recognized transient errors. StoreKit still supplies exact products/prices/eligibility; no static purchase fallback is fabricated. Empty products retain the screen's existing retry path. Generation-bound handles still reject another account's products before checkout. Same-identity stale handles are not silently remapped to a different price or trial offer. A refresh after a rare stale handle remains a follow-up; this branch does not change the install split or offer contract.
- **Offline / flaky network:** retryable preflight operations use 300/900 ms backoff. A fresh offline install still cannot complete required canonical server provisioning/Adapty identify, even when a fallback paywall exists. Mandatory server identity readiness and local PostHog identification remain dependencies under ADR 0011; the lead's integration fix alone does not remove those dependencies. StoreKit also needs an available App Store/account/payment path. This branch does not promise offline purchasing.
- **Ask to Buy / pending:** retain the durable pending operation, deny another checkout, and let an owner-matching later profile confirm recovery. The attribution intent is dropped for explicit pending outcomes, preserving ADR 0084's accepted policy. Apple's `Transaction.updates` supplies approval results. Error 1050 is normalized to pending; cancellation stays silent. A genuinely denied/expired Ask to Buy without a definitive result may require further transaction-status recovery; an empty restore cannot erase an uncertain checkout under ADR 0086.
- **Already subscribed:** code 107 follows the existing restore path without another charge. iOS usually returns a transaction/profile rather than Android's item-already-owned code. Trial ineligibility is represented by the StoreKit product's eligible offer, not by a forced trial. App Store payment restrictions, missing agreements, unavailable products, billing failures and invalid offer signatures require the appropriate App Store/account/configuration correction; retries cannot override them.
- **App backgrounded / process interrupted:** the operation belongs to the runtime, with a journal written before the payment call; it is not cancelled when the Paywall unmounts. Native 4.0.2 observes `Transaction.updates` and unfinished transactions. Unknown exceptions retain recovery. Native scene selection already uses `purchase(confirmIn:)` on iOS 18.2+, addressing the known older UIKit presentation issue. Physical interruption and sheet behavior remain unverified here.
- **StoreKit success but Adapty profile update fails:** verified native transactions are persisted in the SDK and backend validation failure returns a locally recalculated success profile. JavaScript records success for the checkout account even with no access in that profile; existing recovery/restore is used. Server admission remains independent, so a webhook/API outage can still delay admission after a charge. No speculative entitlement bypass is added. Native unverified transactions can instead throw 2005 and are now retained as uncertain recovery.
- **Identity generation changes:** each retry and the boundary immediately before purchase/restore checks identity. The global identity barrier serializes identity-sensitive transitions. A successful StoreKit result records transaction metadata before rejecting a stale live generation. Delayed profiles are still discarded unless their customer UID and generation match. These guards do not prove a real Adapty account transfer; the post-purchase audit owns admission/transfer follow-up.
- **Missing PostHog ID:** the lead is removing identifier attachment as a purchase/restore veto. This branch leaves that method untouched. Analytics capture may be absent when consent is off or canonical analytics identity has not committed; payment robustness must not infer user payment state from analytics presence.
- **iOS 27:** no reproduced purchase-specific regression or primary-source diagnosis was established. The supplied Apple authentication failures concern AuthenticationServices rather than a demonstrated StoreKit defect. No SDK upgrade, native entitlement change or iOS 27 workaround is guessed.
- **Runtime compatibility:** this branch targets the current runtime 7 source (`app-next/app.config.ts:70`). The incident's build 21 is runtime 6. A compatible backport from the runtime 6 source is required for that installed audience; current source cannot be published directly to runtime 6 under ADR 0084. No backport or publication is included here.

## Error-code handling inventory

Inventory covers the installed `react-native-adapty` 4.0.2 / `@adapty/core` 4.0.1 mapping and the pinned Adapty iOS 4.0.2 native additions. It is deliberately phase-sensitive: a retryable read/restore error is not permission to re-open Apple's payment sheet. Newer vendor documentation also names codes not present in the pinned SDK; those remain conservative unknown failures.

- **Bounded automatic retry for activation/identify/reads/explicit restore:** 7 (cloud network), 97 (Android billing timeout), 99 (billing disconnected), 102 (billing service unavailable), 112 (billing network), 1002 (product request), 1010 (receipt refresh), 1011 (restored transactions), 1020 (subscription status), 2004 (backend/server/throttle), 2005 (network), 3101 (fetch timeout). Three total attempts; no unbounded retry and no automatic `makePurchase` retry.
- **Known cancellation:** result `user_cancelled` or legacy code 2. Clear the checkout only durably; emit cancelled failure diagnostics; show no error notice.
- **Pending:** result `pending` or native 1050. Retain recovery, return pending, never grant admission or submit a second checkout.
- **Definite pre-transaction restriction/product/configuration failures:** 1, 3–14, 20, 22, 24, 98, 103, 105, 107, 108, 1000, 1002, 1003, 2002, 2003, 3001, 3005. No automatic payment retry. A pending journal can be cleared because these report failure before a successful transaction; 107 uses restore. Device restrictions, storefront/product availability or configuration may need user/operator action. Code 2002 requires successful activation/readiness rather than a blind purchase retry; code 3005 is an activation-order/configuration defect.
- **Ambiguous after `makePurchase`:** 0, 97, 99, 102, 106, 112, 1004, 1005, 1006, 1010, 1011, 1020, 1030, 2004, **2005**, 2006, **2009**, 3000, 3006, 3007, 3020, 3100, 3101, 9000 and unrecognized errors. Retain recovery and reconcile through restore/independent admission. Some are not valid purchase errors on this iOS build, but a future wrapper or bridge surprise must not erase payment recovery. Code 2009 is response encoding, 3006 is profile-changed, 3100 is wrapper persistence, and 9000 is operation-interrupted.
- **Analytics failure classes:** 2 → cancelled; 3/4/1003 → declined; 7/97/99/102/112/2004/2005/3101 → network; known product/restriction/readiness/receipt/restore/profile-unavailable codes → unavailable; all others → unknown. These are the existing registry values; no event names or properties are added.
- **Newer, unshipped API codes:** 1060 (billing-plan unavailable), 3201 (operation in progress), 3202 (resolver failure), and flow-renderer-only codes are not pre-transaction proofs in the installed wrapper. Do not add blind payment retries for them. This app's annual/monthly plans do not use the newer commitment billing-plan API.

## Why builds 21/22 have no purchase events

The event call sites and shared schema are present. The production adapter, unlike `AnalyticsFake`, drops them with a prefix regular expression. Thus earlier fake-analytics proofs could pass while the shipping adapter emitted nothing. The new proof uses `PaywallScreen` and the real `createPostHogAnalyticsAdapter` with a scripted SDK boundary; it fails against the old filter and captures intent plus cancellation after its removal.

The SDK is not configured for sampling. `POSTHOG_OPTIONS` disables replay/lifecycle/error autocapture and starts opted out; the identity adapter explicitly opts in only when permitted. `allowed()` rechecks live and committed UID/generation before and after super-property registration. The installed PostHog core queues captures persistently, flushes at 20 events or 10 s by default, and React Native flushes on AppState changes even when lifecycle event capture is off. Reset/opt-out intentionally clear queues, so a rapid account switch may discard pending events; no speculative consent bypass or forced payment-blocking flush is added. Those mechanisms cannot explain the deterministic prefix-specific omission while `paywall_error` survives.
